# 核验产物

产物：一段写完、会被人据以行动的文本。本 skill 核验它与来源是否一致，一次扫描给出结论。

核验有两个方向，写进同一份清单：

- 忠实度：产物是否丢失、歪曲、混入或抹平了来源里的内容。
- 事实：产物里的事实主张是否有证据。

读者只做一个决定：这句话改不改。

## 0. 与 `ste` 和 AGENTS.md 的关系

- `ste` 在写作时约束表达。本 skill 在写完后对账内容。本 skill 不检查句长和用词。
- 本 skill 的报告写给用户，必须按 `ste` 写。写报告之前，先加载 `ste`（见 §6）。
- 状态词的定义以 `ste` 术语表第 4 节为准。「已验证」只表示检查已执行且通过。
- 本 skill 的判定词（见 §3）不与 `ste` 的状态词重名。一个词只有一个意思。
- 产物是项目文件（ADR、spec）时，「修正」列的片段按项目自己的写法写。
- 产物是写给用户的汇报时，「修正」列的片段按 `ste` 写。

## 1. 定产物与来源

- 产物：用户指定的文本。没有指定时，是上一条产出的原文。
- 上一条本身是核验报告时，产物上移一级：核验它所核的那份原文。
- 来源：产物据以写成的材料。按来源的强度定范围：
  - 有正式需求（spec、issue、diff）：全量核验。来源的每条需求在产物里都必须有对应。漏项靠这一步发现。
  - 只有会话：只核产物提到的内容。会话来源包括用户的话，和本会话的工具调用记录。
  - 没有来源：只核事实。忠实度写入「未做」，原因写「没有来源」。
- 工具调用记录已丢失时（例如上下文被压缩），不得凭记忆补写。相关条目判「未确认」。
- 产物或来源认不出时，问一次。其余情况不中断。

完成标准：产物与来源各能用一句话指认，核验范围已定。

## 2. 判类型

| 类型 | 典型 | 忠实度问什么 | 这个类型常见的错 |
| --- | --- | --- | --- |
| 结论型 | 完成汇报、总结、审计结论 | 说的和来源一致吗 | 推断写成史实；绝对量词（每次、从来、都）；统计口径悄悄换；把「未运行」写成「通过」；验证范围写大 |
| 计划型 | 待办、步骤、spec 提案、「建议」 | 步骤的前提成立吗 | 命令、路径、版本、前置条件已过期 |
| 提问型 | 追问、选项对比 | 答的是不是所问 | 设问的前提本身就错，整轮讨论作废 |
| 分析型 | 解释、对比、排查结论 | 结论有证据吗 | `路径:行号`、commit、版本号：最像核过，最容易过期 |

取证的排队按「看起来多可信」，不按来源的难易。最像已被验证的句子先核：带句柄的引用、百分比、绝对量词、「已验证」声明。

完成标准：一句话说清类型。说不清，说明产物还没读完。

## 3. 列条目

来源侧：每条需求、约束、优先级、决定，附来源原句。
产物侧：每句事实主张、每句「已完成某事」的声明、越界内容，附产物原句。

合并去重：同一件事占一个条目。证据相同的条目共用一次取证。

每个条目有六个字段：

- 原句：产物原句。`需求-丢失` 的条目没有产物原句，写来源原句。
- 类型：`需求-丢失`、`需求-歪曲`、`需求-混入`、`需求-归因`、`需求-抹平`、`事实-数字`、`事实-版本`、`事实-引用`、`事实-命令行为`、`事实-兼容性`、`越界`。
- 证据：能打开的出处。
- 判定：见下。
- 严重度：见下。
- 修正：`原句 → 新句`。`需求-丢失` 的修正写要补的句子。

判定词只有四个：

- 相符：产物所述与证据一致。证据必须能打开。
- 有误：产物所述与证据冲突。必须写错在哪、正确的说法是什么。
- 未确认：找不到足够的证据。必须写确认方法。
- 未验证：已知有检查可做，但没有做。必须写原因。

「相符」不等于「已验证」。产物自己写了「已验证」时，本 skill 核对的是：该声明与本会话的工具记录是否一致。

严重度只有两档：

- 阻断：读者会据此做错事。
- 轻微：表述走样，不影响行动。

完成标准：产物的每段都有对应的条目，或标「未核」。来源的每条需求都有对应的条目，或标「未出现」。

## 4. 取证

- 只核清单里的条目。同一证据（`路径:行号`、commit、URL）只取一次。证据必须写到能点开。
- 来源的顺序同 AGENTS.md §12：仓库代码、官方文档、实际运行；然后是权威二次来源；最后是网页。
- 用户说的和你自己说的，都当作待检查的假设。
- 产物声明运行行为时，资料不能代替运行结果。这类声明包括「测试通过」「修复有效」。
- 只有资料、没有运行结果或本会话的工具记录时，判「未确认」，并写确认方法。

完成标准：判定为「相符」或「有误」的条目，都有能打开的证据。取不到证据的条目判「未确认」，并附一条可执行的确认方法。

## 5. 级联与不合格

- 级联：某条「有误」会使依赖它的下游条目失效。下游条目指基于它的步骤、结论和后续问题。这些条目判「未确认」，并写「受影响：依赖 #n」。
- 不合格的默认阈值：「阻断」超过 3 条，或「需求-丢失」与「需求-歪曲」合计过半。用户可以改阈值。
- 判不合格时，给重做要点：缺什么、错在哪一层。修补一份本身就错的产物，比重写贵。

## 6. 汇报

先加载 `ste` 技能。它是显式技能，不会自动加载。路径以技能列表给出的为准。

报告按判定分组。每组一个标题，组内列出全部相关条目。不用表格。
原因：证据和修正是整句，放进单元格会换行错位。「相符」的行还会淹没必须改的行。

结构如下，没有内容的组删除：

```
<一句结论>：核 N 条，相符 a、有误 b（阻断 c）、未确认 d、未验证 e。

**范围**：<核了什么>。

**有误：阻断（c）**
- #1 「<产物原句>」（<类型>）
  - 证据：<出处>。
  - 修正：`原句 → 新句`。

**有误：轻微（n）**
- #2 「<产物原句>」（<类型>）
  - 证据：<出处>。
  - 修正：`原句 → 新句`。

**未确认（d）**
- #3 「<产物原句>」（<类型>）
  - 证据：<现有的证据；没有就写「无」>。
  - 确认方法：<一个可执行的动作>。

**未验证（e）**
- #4 「<产物原句>」（<类型>）
  - 原因：<已知有检查可做，但没有做的原因>。

**相符（a）**
- #5 「<产物原句>」 — <证据位置>。

**未做**
- <没有核的内容> — <原因>。

**待确认**
- <由用户决定的事项，或来源缺少的内容>。

<请求决定>
```

填好的示例：

```
改 2 处后采纳：核 5 条，相符 2、有误 2（阻断 1）、未确认 1。

**范围**：忠实度全量，事实 3 条。

**有误：阻断（1）**
- #1 「已验证：`npm test` 通过」（事实-命令行为）
  - 证据：本会话只运行过 `npm test auth`，48 项通过。
  - 修正：`npm test` 通过 → `npm test auth` 通过（48 项）。

**有误：轻微（1）**
- #2 「所有端都已适配」（需求-抹平）
  - 证据：issue 只列出 web 和 android。
  - 修正：所有端 → web 和 android。

**未确认（1）**
- #3 「iOS 构建正常」（事实-兼容性）
  - 证据：无。本会话没有 iOS 的运行记录。
  - 确认方法：在 iOS 环境运行构建命令。

**相符（2）**
- #4 「`auth/refresh.ts:42` 刷新前不检查」 — 已读取该文件，第 42 行相符。
- #5 「删除 3 处重复日志」 — `git diff` 显示删除 3 处。
```

规则：

- 结论四选一：`可采纳`、`改 K 处后采纳`、`不合格，建议重做`、`只核了事实`。
- 产物没有可核内容时，第一句写「无可核内容。」不给结论。
- 范围举例：「忠实度全量，事实 6 条」「只有会话，没有需求来源」「没有来源，忠实度未核」。
- 组的顺序固定：有误（阻断）、有误（轻微）、未确认、未验证、相符。读者先看到必须改的。
- 条目编号 `#n` 全文连续。组内按条目在产物中的位置排序。
- 「有误」和「未确认」的条目写三行：原句、证据、修正或确认方法。
- 「未验证」的条目写原句和原因。「相符」的条目每条一行。
- 「修正」只写受影响的部分，并且只写已有证据支持的内容。
- 修正依赖来源里没有的内容时，不写进「修正」。把它列入「待确认」。
- 有级联时，下游条目多写一行：「受影响：依赖 #n」。
- 全部相符时，一句话确认：「可采纳：核 N 条，全部相符。」

收尾按 `ste` 的「请求决定」格式：

```
<一句：是否按上面的修正修改产物>。

1. 全部采纳（推荐）— 按修正逐条替换，含轻微项。
2. 只采纳阻断项 — 轻微项保持原样。
3. 不改 — 产物保持原样。
```

判不合格时，选项 1 改为「按重做要点重写（推荐）」。
用户也可以按编号选择，例如 `#1 #3`。

## 不做

- 代码实现是否满足需求：交给 `code-review` 的 Spec 轴，拿 diff 对 issue。本 skill 只核文字主张。
- 审美、偏好和「该不该做」：主观，不核。
- 「能不能做、做了会怎样」：是事实，必须核。
- 同一会话自核有盲区：写产物和核产物的是同一个上下文。重要产物，委托新会话或 subagent 核验，来源写入文件传递。
