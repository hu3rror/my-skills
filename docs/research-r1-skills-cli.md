## 1. Overlay / patch / update — is ADR-0002's "no overlay or patch mechanism" still current?

**Verified fact**: Still current. The CLI has **no overlay, patch, or local-adaptation mechanism** in any documented surface as of v1.7.0 / `main`:

- `skills --help` (help text in `src/cli.ts` `showHelp()`) lists exactly these commands: `add`, `use`, `remove`/`rm`, `list`/`ls`, `find`, `update`/`upgrade`, `init`, `experimental_install`, `experimental_sync`. No patch/overlay/merge command exists.
- The `add` option set (`parseAddOptions` in `src/add.ts`, `AddOptions` interface) is: `-g/--global`, `-a/--agent`, `-s/--skill`, `-l/--list`, `-y/--yes`, `--copy`, `--metadata`, `--subagent`, `--all`, `--full-depth`, `--json`. Nothing overlay-like.
- The install model is copy-or-symlink of the whole skill folder (see Q2); `update` re-downloads from the recorded source/ref and **overwrites** — there is no diff/merge step, and v1.5.8 added "Clean up skills deleted upstream on `skills update` (#1218)" (releases API), i.e. update actively *removes* local content rather than preserving deviations.
- ADR-0002 (`docs/adr/0002-patch-strategy-fork-semantics-with-manifest.md`, hu3rror/my-skills): "vercel-labs/skills has no overlay or patch mechanism, so adapting upstream content had to happen somewhere persistent … rely on the CLI's absent overlay mechanism (not possible)." — matches the CLI's current state; the repo's own README states the same: "Editing `~/.agents/skills` directly works until the next `npx skills update` re-downloads from upstream and silently discards local edits" (README.md, hu3rror/my-skills).

**Source**: `https://raw.githubusercontent.com/vercel-labs/skills/main/src/cli.ts` (help text); `https://raw.githubusercontent.com/vercel-labs/skills/main/src/add.ts` (AddOptions/parseAddOptions); releases API `api.github.com/repos/vercel-labs/skills/releases` (v1.5.8 changelog #1218); `https://raw.githubusercontent.com/hu3rror/my-skills/main/docs/adr/0002-patch-strategy-fork-semantics-with-manifest.md`; `https://raw.githubusercontent.com/hu3rror/my-skills/main/README.md`.
**Confidence**: High (source-level, not just README; no counter-evidence found in `main`).

## 2. Discovery & copy semantics (`-s '*'`, SKILL.md presence, whole-folder copy, folder hashing)

**Verified facts**:

**(a) What counts as a skill.** A directory with a **`SKILL.md` file whose YAML frontmatter has string `name` and `description`** (`src/skills.ts`: `hasSkillMd()` + `parseSkillMd()`; invalid/missing fields → warn and skip). Discovery walks known container dirs (repo root at depth 1; `skills/`, `skills/.curated`, `skills/.experimental`, `skills/.system`, and per-agent `*.skills/` dirs incl. `.pi/skills` at up to **3 levels** deep, `DEFAULT_SKILL_CONTAINER_DEPTH`); a `SKILL.md` found at a shallower level shadows deeper ones; falls back to a full recursive scan when nothing is found; `--full-depth` forces recursive. `metadata.internal: true` hides a skill from discovery unless `INSTALL_INTERNAL_SKILLS=1` or the skill is explicitly named; since v1.5.23, `-s '*'` **excludes internal skills** (#1909). `-s '*'` (`options.skill.includes('*')`) selects **all** discovered skills (src/add.ts).
Note: the repo's own README already documents the depth-3 rule and relies on it (`skills/mattpocock/<category>/<name>/` is the deepest layout).

**(b) Install copies the whole skill folder, not just SKILL.md.** `src/installer.ts` `installSkillForAgent()` → `copyDirectory(skill.path, dest, agentType)` — recursive copy of the entire directory tree. Exclusions at copy time are only the file `metadata.json` and the dirs `.git`, `__pycache__`, `__pypackages__`. The copy dereferences symlinks and preserves file modes. In symlink mode the folder is still first *copied* to the canonical store `.agents/skills/<name>` (or `~/...` for `-g`), then symlinked into agent dirs; in copy mode it is written per-agent. The `add.ts` comment for the disk path explicitly says root-level skills are "copied recursively … so their `scripts/`, `references/`, `assets/`, etc. are installed too" (issue #1603; see also v1.5.18 changelog "fix: install full skill directory for root-level SKILL.md repos (#1609)").
Nuance — GitHub "blob fast path": for GitHub sources the CLI tries a snapshot download **only** when the repo/owner is allowlisted (`BLOB_ALLOWED_OWNERS = vercel, vercel-labs, heygen-com, remotion-dev`, plus per-repo `BLOB_ALLOWED_REPOS`); that path writes only the snapshot's files (which may be just `SKILL.md`; v1.5.25 "fall back when skill snapshots omit files (#2069)"). Well-known/skills.sh sources write all files declared in the index. **`hu3rror/my-skills` is not allowlisted**, so its install path is git clone → whole-folder copy.

**(c) The lock files hash entire folders, and the hash changes when any file in the folder changes.**
- Global lock `~/.agents/.skill-lock.json` (or `$XDG_STATE_HOME/skills/.skill-lock.json`), schema version 3, entry `skillFolderHash`: "GitHub tree SHA for the entire skill folder. This hash changes when ANY file in the skill folder changes. Fetched via GitHub Trees API" (`src/skill-lock.ts`). `add.ts` fetches the repo tree once and extracts the folder SHA; for non-GitHub/non-blob sources it falls back to `computeSkillFolderHash()` over the folder (v1.5.7 changelog: "fix: compute skillFolderHash for non-GitHub git sources (#934)").
- Project lock `skills-lock.json` at the repo root (schema v1, explicitly "meant to be checked into version control"): entry `computedHash` = **SHA-256 over all files of the skill folder** (recursive, path-ordered, path included in the hash; skips `.git` and `node_modules`) — `src/local-lock.ts` `computeSkillFolderHash()`.

**(d) Consequence for repo-internal records.** Because install copies whole folders and both lock hashes cover whole folders, **any file placed inside a skill folder is distributed to the store** (`~/.agents/skills`) on `npx skills add hu3rror/my-skills -a universal -s '*' -g -y` and re-distributed on `skills update`. Repo-internal records (PATCHES.md, ADR docs, scripts) therefore cannot live inside a skill folder "without being distributed" — the only escapes are the copy-time exclusions (`metadata.json`, `.git/`, `__pycache__/`, `__pypackages__/`). The repo already encodes this conclusion in practice: PATCHES.md, ADRs, scripts and GLOSSARY live at repo root/`docs/`/`scripts/`, not inside `skills/*`; even the local-only `references/` assets added under `skills/awesome-copilot/create-readme/` are acknowledged as distributed ("new local-only assets under `skills/awesome-copilot/create-readme/references/`", PATCHES.md row #10).

**Sources**: `https://raw.githubusercontent.com/vercel-labs/skills/main/src/skills.ts`; `…/src/add.ts` (blob allowlist, `-s '*'` branch, lock writes); `…/src/installer.ts` (copyDirectory, EXCLUDE_FILES/DIRS, canonical dir); `…/src/skill-lock.ts`; `…/src/local-lock.ts`; README (discovery section, direct-download limits, install methods); releases API (v1.5.23 #1909, v1.5.18 #1609, v1.5.7 #934).
**Confidence**: High.

## 3. CLI-native exclude / pin / lock — what could absorb parts of PATCHES.md?

**Verified facts**:
- **Exclude: no CLI flag exists.** `--skill <names>` is an include-filter; there is no `--exclude`/deny-list anywhere in the help text or `AddOptions`. The only native exclusion mechanisms are (i) the frontmatter `metadata.internal: true` flag (hidden from discovery and from `-s '*'` unless `INSTALL_INTERNAL_SKILLS=1`) and (ii) copy-time file exclusions (`metadata.json`, `.git`, `__pycache__`, `__pypackages__`). PATCHES.md's "Excluded from vendor sync" curation (e.g. mattpocock `skills/in-progress`, `skills/misc`, `wizard`, `triage`, `to-questionnaire`) is enforced by the repo's own `scripts/vendor-sync.mjs`, not by the CLI.
- **Pin: yes, source-level pinning exists — commit-SHA pinning is a shipped feature (v1.5.24: "feat: support installing skills pinned to a commit SHA (#1439)").** Syntax (src/source-parser.ts): a `#<ref>` fragment on git-like sources (`owner/repo#<sha>`, `owner/repo#<branch-or-tag>`, with optional `#<ref>@<skill>` skill filter), or a `/tree/<branch>` GitHub/GitLab URL, or Azure `version` query. The chosen ref is stored in both lock entries as `ref` and respected by `update` (v1.5.23 "don't delete a skill from the same repo pinned to a different ref (#1953)"; v1.5.22 "preserve locked GitHub host during updates (#1837)"; v1.5.24-adjacent "bypass blob snapshots for explicit refs (#1934)"). Note the CLI pins per *skill source at install time*; PATCHES.md's "Upstream references" pins are per *source for diff-baseline checking* and are parsed by `vendor-sync.mjs` (`parseUpstreamRefs()`), so the CLI pin feature overlaps conceptually but does **not** consume the manifest's pins.
- **Lock: yes, two locks — but they track installed skills, not patch manifests.** Global `~/.agents/.skill-lock.json` (v3: source, sourceType, sourceUrl, `ref`, `skillPath`, `skillFolderHash`, installedAt/updatedAt; used by `update`/`remove` bookkeeping) and project `skills-lock.json` (v1: source, sourceUrl, `ref`, `skillPath`, `computedHash`, Eve `subagents`; `experimental_install` restores from it). Neither records per-file patch data, so they cannot absorb PATCHES.md's A-class file list or its patch semantics.
- **Net**: of the three PATCHES.md concerns (patch protection, excluded roots, upstream pins), the CLI can natively absorb only *source pinning* (and even then per-skill, not per-source diff baselines). Nothing native replaces the patch manifest or the excluded-roots curation; ADR-0002's fork-semantics decision remains the only mechanism that protects patches.

**Sources**: `src/cli.ts` (help), `src/add.ts` (AddOptions/parseAddOptions), `src/source-parser.ts` (parseFragmentRef, tree-URL refs), `src/skill-lock.ts`, `src/local-lock.ts`, releases API (v1.5.24 #1439), PATCHES.md + `scripts/vendor-sync.mjs` (hu3rror/my-skills).
**Confidence**: High for absence of flags (help + parser source); pin syntax verified from source + release notes.

## 4. CLI version pinning and churn; issue #2039 status

**Verified facts**:
- **Pinning the CLI version is feasible** via npx: `npx skills@<version> add …` (the issue reporter's own commands use `npx skills@latest`; the project's own README/PATCHES use bare `npx skills add …`). npm dist-tags: `latest` = **1.7.0**, `snapshot` = 1.5.23-snapshot.2 (registry API). v1.7.0 requires **Node ≥ 22.20.0** (`engines`), ships bin `skills` + `add-skill` → `bin/cli.mjs`, published by GitHub Actions with SLSA provenance.
- **Churn is high.** vercel-labs/skills was created 2026-01-14; the npm package `skills` (squatted legacy name — 1.0.0 from 2016 was an unrelated "stackexchange tags" package) was taken over with 1.0.1 (~2026-01-16) and has shipped dozens of versions since. Release cadence from the releases API: v1.4.9 (April) → v1.5.0 (2026-04-12), v1.5.1 (04-17), v1.5.7 (05-14), … v1.5.16 (07-10), v1.5.17 (07-13), v1.5.18/19 (07-16), v1.5.20 (07-22), v1.5.21 (07-30), v1.5.22 (08-05), v1.5.23 (08-18), v1.5.24 (09-06), v1.5.25 (09-08), v1.5.26 (09-11), v1.6.0 (09-16), **v1.7.0 (09-17)** — ~24 releases in ~5 months, i.e. **~1–2 releases/week** in Jul–Sep 2026.
- **Issue #2039 is real, open, and still unfixed in `main`.** The issue (filed 2026-08-23 against v1.5.23) documents that `--skill=<name>` (equals form) is silently discarded by `parseAddOptions`, falling through to "install everything" (in non-interactive contexts the `selectAll: true` multiselect resolves to all). The reporter's follow-up comment (2026-08-23) generalizes: **any unrecognized `-`-prefixed token is silently dropped** by `add`, `use`, `remove`, `list`, `sync` (only `--owner=` in `find` is handled), with two opposite failure modes — `add` over-installs, `remove` silently no-ops. I verified directly in current `main`'s `parseAddOptions` (src/add.ts): the `--skill`/`-s`, `--agent`/`-a`, `--subagent` branches match exact tokens only, and the final catch-all is `else if (arg && !arg.startsWith('-')) source.push(arg)` — i.e. **unknown `-` flags are still silently discarded**. The fix PR **vercel-labs/skills#2086** ("fix(cli): support equals-sign syntax for --skill, --agent … (#2039)", created 2026-08-28, last updated 2026-09-17) is **open and unmerged** (`merged_at: null`; timeline cross-reference event). So the bug is present in v1.7.0. The my-skills repo already documents this precisely in PATCHES.md: "the equals form (`--skill=<name>`) is silently discarded by the CLI and falls back to a full install (vercel-labs/skills#2039)". A related symptom also hit upstream mattpocock/skills (issue #1012 "The documented one-skill install installs all 37 …").
- **Practice in this repo**: the distribution chain runs the CLI **unpinned** — README documents `npx skills add hu3rror/my-skills -a universal -s '*' -g -y` (bare `npx skills` = latest); `scripts/vendor-sync.mjs` doesn't invoke the CLI at all (it uses `git clone --depth 1` per source). So version pinning is feasible but not currently practiced, and given the weekly release cadence plus the #2039 class of silent-behavior bugs, pinning (`npx skills@<pinned-version> …`) would be a cheap hardening step for the chain.

**Sources**: issue JSON/comments/timeline `api.github.com/repos/vercel-labs/skills/issues/2039` (+ `/comments`, `/timeline` — includes PR #2086 state); `https://raw.githubusercontent.com/vercel-labs/skills/main/src/add.ts` (parseAddOptions, verified current); releases API; `https://registry.npmjs.org/skills` and `/skills/1.7.0`; hu3rror/my-skills README.md, PATCHES.md; mattpocock/skills#1012 (timeline cross-ref).
**Confidence**: High for bug presence and unmerged fix (issue + source + PR state); note main may have moved since my fetch, but PR #2086 being unmerged and the changelogs of v1.5.25–v1.7.0 containing no parser-validation fix support the "still present" reading.
